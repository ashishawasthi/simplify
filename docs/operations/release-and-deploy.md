How a change gets from a branch to https://simplify.whiz.coach/: the three GitHub Actions workflows, the deploys CI does not do, and the checklist before merging to `main`. Running the tests locally is in [local development](/operations/local-development.md); the project the deploys land in is in [cloud project](/operations/cloud-project.md).

## CI workflows

| Workflow | Runs on | What it does |
|---|---|---|
| `.github/workflows/tests.yml` | every pull request and every push to `main` | Node 22, Java 21 (Temurin), `firebase-tools@15`, `npm ci --prefix functions`; then every `tools/test-*.mjs` in turn (stops at the first failure), then `node tools/smoke.mjs` in headless Chrome. No secret, no deploy. 20-minute timeout. |
| `.github/workflows/firebase-hosting-merge.yml` | push to `main` | `FirebaseExtended/action-hosting-deploy@v0` with `channelId: live`: deploys **Hosting only** to the live site, so `simplify.whiz.coach` and `simplify-special.web.app` update together. |
| `.github/workflows/firebase-hosting-pull-request.yml` | pull requests from branches of this repository (fork PRs are skipped) | The same action without a channel: deploys Hosting to a preview channel named after the PR (e.g. `pr2-money-tools`) and comments its URL on the PR. Preview channels expire after 7 days. |

The two Hosting workflows were generated by `firebase init hosting:github`. They are separate from `tests.yml` and do not wait for it: a push to `main` deploys even if the tests on that commit fail. Run the checklist below before merging.

### The deploy secret

Both Hosting workflows authenticate with the repository secret `FIREBASE_SERVICE_ACCOUNT_SIMPLIFY_SPECIAL`, a JSON key for the service account `github-action-1331591442@simplify-special.iam.gserviceaccount.com`. `firebase init hosting:github` created the account, its key and the secret together (2026-08-12). The account holds Firebase Hosting Admin plus the other roles that command grants: Cloud Functions Developer, Firebase Authentication Admin, Cloud Run Viewer, API Keys Viewer and Service Usage Consumer. The workflows use it only for Hosting.

To replace it, run `firebase init hosting:github` again, or create a key for that account in Google Cloud IAM and paste the JSON into the secret. Never commit a key.

## What CI does not deploy

Security rules, Firestore indexes and Cloud Functions are deployed by hand, from a machine signed in with `firebase login` as a project owner. `.firebaserc` makes `simplify-special` the default project; the targets are those in `firebase.json`.

| Deploy | Command | Notes |
|---|---|---|
| Hosting (by hand) | `firebase deploy --only hosting` | Same as the merge workflow; only needed if CI is unavailable. |
| Rules and indexes | `firebase deploy --only firestore:rules,firestore:indexes,storage` | `firestore.rules`, `firestore.indexes.json`, `storage.rules`. Run `node tools/test-rules.mjs` first. `storage.rules` reads Firestore, which needs `roles/firebaserules.firestoreServiceAgent` on the Storage service agent; an interactive `--only storage` deploy offers to grant it (already granted, see [cloud project](/operations/cloud-project.md#storage-rules-can-read-firestore)). |
| Cloud Functions | `firebase deploy --only functions` (or `--only functions:writePage` for one) | The `predeploy` runs `tools/copy-class-markdown.mjs`, so `functions/class-markdown.js` is refreshed from `public/js/class-markdown.js`. Uploads `functions/` except `node_modules`, `test` and `*.local` (so `functions/.env.local` and its fake-model switch never deploy). The deployer needs permission to act as `simplify-functions@simplify-special.iam.gserviceaccount.com`. Run `node tools/test-functions.mjs` first. |

Avoid a bare `firebase deploy`: it deploys everything at once, functions included.

Data the rules depend on is written by the owner's tools, not by a deploy: the institutions (`tools/seed-institutions.mjs`) and, once, the status of coach profiles made before coach approval (`tools/migrate-coaches.mjs`) — both in [admin and approvals](/coach/admin-and-approvals.md#switching-coach-approval-on-once).

Order matters when a change spans them. A change whose new pages or app code need new rules or a new callable: deploy rules and functions first, then merge the Hosting change. A change that removes something: merge the Hosting change first, then tighten the rules or delete the function.

## Release checklist

Before merging to `main`:

1. **Tests.** Every `tools/test-*.mjs` passes (see [local development](/operations/local-development.md#unit-tests)).
2. **Smoke.** `node tools/smoke.mjs` passes.
3. **Docs.** `node tools/build-docs-index.mjs --check` passes, and the documents that own what changed say what the code now does.
4. **Stamp.** After any change under `public/`, `node tools/stamp.mjs`, and commit what it writes: every file's revision in `ASSETS` in `public/sw.js` (so installed apps see the new version and fetch only the changed files) and the pages' modulepreload lists. There is no version number to bump. `tools/test-assets.mjs` fails if it was forgotten. Two branches that both changed `public/` may conflict in `ASSETS`: take either side and run it again. How a new version reaches devices is in [offline and updates](/platform/offline-and-updates.md).
5. **Try it on real devices.** Run the change locally on an Android phone and an iPad (including offline, from port 5050), since those are what learners use.

### The guide comes after testing

The learner guide (`public/guide.html`, `public/guide/*.html`) and its screenshots are updated only **after** the app change has been tested locally on an Android phone and an iPad, never alongside it, so the words and pictures describe what actually ships. Order: build → test (tests, smoke, devices, offline) → update the guide pages and retake the screenshots with `tools/shoot-guide.mjs` → `node tools/stamp.mjs`. The guide is a topic menu with one short page per topic: add a page for a new feature rather than growing an existing one, with a button on the guide menu (`stamp.mjs` adds it to `ASSETS`).

## Addresses

- **https://simplify.whiz.coach/** is the only address to share or link to. It is a custom domain on the Hosting site, added under **Hosting → Custom domains** in the Firebase console.
- Every absolute URL in the app and the guides (canonical, Open Graph, the QR codes, instructions) uses `https://simplify.whiz.coach/`. Links between pages stay relative, so they also work offline and on PR previews.
- `https://simplify-special.web.app/` serves the same files but is a **separate origin**: its localStorage, saved numbers, settings and installed app are its own and do not carry over. Each PR preview URL is another origin again, and it reads the production Firestore and Storage. A preview's host is not in Firebase Authentication's authorized domains, so the coach app's Google sign-in is refused there.

## Repository conventions

- **Linear history.** `main` has no merge commits: pull requests are merged with rebase-merge (never a merge commit). GitHub does not enforce it (merge commits are still enabled in the repository settings and `main` has no branch protection), so choose **Rebase and merge**.
- Work happens on a branch; `main` is what is live.
