How a change gets from a branch to https://simplify.whiz.coach/: the three GitHub Actions workflows, deploying by hand when CI can't, and the checklist before merging to `main`. Running the tests locally is in [local development](/operations/local-development.md); the project the deploys land in is in [cloud project](/operations/cloud-project.md).

## CI workflows

| Workflow | Runs on | What it does |
|---|---|---|
| `.github/workflows/tests.yml` | every pull request and every push to `main` | Node 22, Java 21 (Temurin), `firebase-tools@15`, `npm ci --prefix functions`; then every `tools/test-*.mjs` in turn (stops at the first failure), then `node tools/smoke.mjs` in headless Chrome. No secret, no deploy. 20-minute timeout. |
| `.github/workflows/firebase-hosting-merge.yml` | push to `main`, or by hand (**Run workflow**) | Three jobs in turn, each only if the one before succeeded: **tests** (`tests.yml`, called as a reusable workflow); **backend**: `npm ci` in `functions/`, then `firebase-tools@15 deploy --only functions,firestore:rules,firestore:indexes,storage --non-interactive --force`; **hosting**: `FirebaseExtended/action-hosting-deploy@v0` with `channelId: live`, so `simplify.whiz.coach` and `simplify-special.web.app` update together. One deploy at a time (`concurrency: deploy-live`); a newer merge waits for the running one. |
| `.github/workflows/firebase-hosting-pull-request.yml` | pull requests from branches of this repository (fork PRs are skipped) | The same action without a channel: deploys Hosting to a preview channel named after the PR (e.g. `pr2-money-tools`) and comments its URL on the PR. Preview channels expire after 7 days. |

Nothing on `main` goes live unless every test passes on that commit. The backend goes before the website, so pages never go live ahead of the rules or callables they need. `--force` makes the live backend exactly what `main` says: a function or index removed from the repository is deleted. The pull-request workflow was generated by `firebase init hosting:github` and does not wait for the tests (a preview is harmless). Run the checklist below before merging anyway: a failure on `main` means nothing deploys.

### The deploy secret

Both Hosting workflows authenticate with the repository secret `FIREBASE_SERVICE_ACCOUNT_SIMPLIFY_SPECIAL`, a JSON key for the service account `github-action-1331591442@simplify-special.iam.gserviceaccount.com`. `firebase init hosting:github` created the account, its key and the secret together (2026-08-12), with Firebase Hosting Admin, Cloud Functions Developer, Firebase Authentication Admin, Cloud Run Viewer, API Keys Viewer and Service Usage Consumer. For the backend deploy the owner added (2026-09-25): **Service Account User on `simplify-functions@simplify-special.iam.gserviceaccount.com` and on `simplify-special@appspot.gserviceaccount.com` only** (not project-wide: the first is what the functions run as; the second the CLI insists on, and it holds no roles — see [cloud project](/operations/cloud-project.md#the-functions-service-account)), **Artifact Registry Writer** (the functions' build images), **Firebase Rules Admin** and **Cloud Datastore Index Admin**. The functions need no secret of their own: they reach Gemini as `simplify-functions`. The key can therefore change the live backend, not just the website; only workflow runs on `main` (and preview runs from this repository's own branches) can read it — pull requests from forks never get secrets. The functions image registry (`gcf-artifacts`, asia-southeast1) keeps a 1-day cleanup policy, set once by the owner, so CI never needs to set one.

To replace it, run `firebase init hosting:github` again, or create a key for that account in Google Cloud IAM and paste the JSON into the secret. Never commit a key.

## Deploying by hand

Only when CI is unavailable, or for a one-off: from a machine signed in with `firebase login` as a project owner. `.firebaserc` makes `simplify-special` the default project; the targets are those in `firebase.json`. What `main` says is what the next merge deploys anyway, so a hand deploy of anything not on `main` is undone by it.

| Deploy | Command | Notes |
|---|---|---|
| Hosting (by hand) | `firebase deploy --only hosting` | Same as the merge workflow's last job. |
| Rules and indexes | `firebase deploy --only firestore:rules,firestore:indexes,storage` | `firestore.rules`, `firestore.indexes.json`, `storage.rules`. Run `node tools/test-rules.mjs` first. `storage.rules` reads Firestore, which needs `roles/firebaserules.firestoreServiceAgent` on the Storage service agent; an interactive `--only storage` deploy offers to grant it (already granted, see [cloud project](/operations/cloud-project.md#storage-rules-can-read-firestore)). |
| Cloud Functions | `firebase deploy --only functions` (or `--only functions:writePage` for one) | The `predeploy` runs `tools/copy-class-markdown.mjs`, so `functions/class-markdown.js` is refreshed from `public/js/class-markdown.js`. Uploads `functions/` except `node_modules`, `test` and `*.local` (so `functions/.env.local` and its fake-model switch never deploy). The deployer needs permission to act as `simplify-functions@simplify-special.iam.gserviceaccount.com`. Run `node tools/test-functions.mjs` first. |

Avoid a bare `firebase deploy`: it deploys everything at once, functions included.

Data the rules depend on is written by the owner's tools, not by a deploy: the institutions (`tools/seed-institutions.mjs`) and, once, the status of coach profiles made before coach approval (`tools/migrate-coaches.mjs`) — both in [admin and approvals](/coach/admin-and-approvals.md#switching-coach-approval-on-once).

Order matters when a change spans them. The merge workflow deploys the backend first, which suits a change that adds rules or a callable. A change that removes something the live website still uses (tightens a rule, deletes a callable) should go in two merges: first the website change, then the backend one. By hand: backend first when adding, website first when removing.

## Release checklist

Before merging to `main`:

1. **Tests.** Every `tools/test-*.mjs` passes (see [local development](/operations/local-development.md#unit-tests)).
2. **Smoke.** `node tools/smoke.mjs` passes.
3. **Docs.** `node tools/build-docs-index.mjs --check` passes, and the documents that own what changed say what the code now does.
4. **New public file → `ASSETS`.** Every new file under `public/` (outside `public/coach/`) goes into `ASSETS` in `public/sw.js`, pages by clean URL. `tools/test-assets.mjs` fails otherwise.
5. **Bump `CACHE`.** Change `CACHE` in `public/sw.js` (`simplify-v<N>` → `simplify-v<N+1>`) for any change to a file the service worker precaches: HTML, CSS, JS, the manifest, a picture or a guide screenshot. Without a new `CACHE`, installed apps keep serving the old files however long they stay open. Skip it only when nothing under `public/` changed, or only `public/coach/` did (the service worker never caches the coach app). How a new `CACHE` reaches devices is in [offline and updates](/platform/offline-and-updates.md).
6. **Try it on real devices.** Run the change locally on an Android phone and an iPad (including offline, from port 5050), since those are what learners use.

### The guide comes after testing

The learner guide (`public/guide.html`, `public/guide/*.html`) and its screenshots are updated only **after** the app change has been tested locally on an Android phone and an iPad, never alongside it, so the words and pictures describe what actually ships. Order: build → test (tests, smoke, devices, offline) → update the guide pages and retake the screenshots with `tools/shoot-guide.mjs` → bump `CACHE`. The guide is a topic menu with one short page per topic: add a page for a new feature rather than growing an existing one, with a button on the guide menu and an `ASSETS` entry.

## Addresses

- **https://simplify.whiz.coach/** is the only address to share or link to. It is a custom domain on the Hosting site, added under **Hosting → Custom domains** in the Firebase console.
- Every absolute URL in the app and the guides (canonical, Open Graph, the QR codes, instructions) uses `https://simplify.whiz.coach/`. Links between pages stay relative, so they also work offline and on PR previews.
- `https://simplify-special.web.app/` serves the same files but is a **separate origin**: its localStorage, saved numbers, settings and installed app are its own and do not carry over. Each PR preview URL is another origin again, and it reads the production Firestore and Storage. A preview's host is not in Firebase Authentication's authorized domains, so the coach app's Google sign-in is refused there.

## Repository conventions

- **Linear history.** `main` has no merge commits: pull requests are merged with rebase-merge (never a merge commit). GitHub does not enforce it (merge commits are still enabled in the repository settings and `main` has no branch protection), so choose **Rebase and merge**.
- Work happens on a branch; `main` is what is live.
